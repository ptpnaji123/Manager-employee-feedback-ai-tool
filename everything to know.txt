Create:

config/feedback_framework.json

Put:

{
  "name": "Situation - Behaviour - Impact",
  "steps": [
    {
      "name": "Situation",
      "description": "Describe when and where the issue occurred specifically."
    },
    {
      "name": "Behaviour",
      "description": "Describe the observable action rather than characterising the person."
    },
    {
      "name": "Impact",
      "description": "Explain the concrete effect on the team, client or work."
    },
    {
      "name": "Listen",
      "description": "Give the employee an opportunity to explain their perspective."
    },
    {
      "name": "Agree on change",
      "description": "Agree on what should change."
    },
    {
      "name": "Agree how it will be checked",
      "description": "Agree how progress will be followed up."
    }
  ]
}

Why do this?

Because the brief says the framework may eventually change by HR without engineering involvement.

So you can say:

"I externalised the framework into configuration so the coaching logic doesn't depend on hardcoded HR policy."

That's a good interview discussion point.

safe_employee_context = build_safe_employee_context(employee)

creates a restricted version.

This is an important design decision for your case study.







We’ll build Prepare as a separate coaching service rather than mixing it into the Rehearse prompt.

The Prepare mode should take the manager's situation and help them turn it into:

Situation — when/where
Behaviour — observable action
Impact — concrete effect
then suggest how to listen, agree a change, and decide how to check it

It also needs to handle the four probe cases without exposing confidential data or helping the manager make unsupported claims.
